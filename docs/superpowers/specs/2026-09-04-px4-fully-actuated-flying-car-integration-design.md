# PX4 v1.17 全驱六旋翼与飞行汽车整合设计

## 1. 目标

以现有全驱 PX4 v1.17 代码树为唯一基线，在新目录 `D:\PX4-v1.17` 中整合飞行汽车 80003 的真机与 Gazebo Classic 功能。整合后的同一套源码通过 `SYS_AUTOSTART` 选择构型：

- `6003`：全驱六旋翼；
- `6004`：全驱六旋翼加 HX-30HM 机械臂；
- `80003`：标准四旋翼加差速轮飞行汽车；
- 其他机架编号：保持 PX4 v1.17 原有行为。

真机目标板为 Pixhawk 6C，主要构建目标为 `px4_fmu-v6c_default`。

## 2. 范围

### 2.1 纳入范围

- 6003/6004 的现有全驱控制分配、姿态控制、位置控制、参数、机架脚本和仿真支持；
- 6004 的 HX-30HM 机械臂驱动和 Pixhawk 6C TELEM2 配置；
- 80003 的机架脚本、专属默认参数、应用启动脚本、飞车模式状态机和差速轮执行器映射；
- 80003 所需的 Gazebo Classic 模型、世界、launch 文件、MAVROS 启动配置和专项测试工具；
- 共享文件中的语义合并，以及普通 PX4 多旋翼路径的回归测试。

### 2.2 不纳入范围

- 不修改两个原始源目录中的既有控制代码；新成果仅存放在 `D:\PX4-v1.17`；
- 不将 80004/80005 八旋翼实验构型注册为本次正式构型；
- 不复制飞车代码树中的 `.bak`、历史备份、构建输出和无关实验资产；
- 不改变标准四旋翼控制律、输出映射或默认启动行为；
- 不新增独立的第二套 Pixhawk 6C 固件目标。

## 3. 选定方案

采用以全驱版本为基线的选择性语义合并：先复制干净的全驱代码树到目标目录，再按依赖链移植 80003。对 Commander、控制器、ROMFS、CMake 和 Pixhawk 6C board 配置等双方均有修改的文件逐段合并，不执行整树覆盖。

放弃以下方案：

- 分立固件目标：隔离较强，但无法仅通过机架参数选择构型，并增加固件维护成本；
- 飞车整树覆盖后补回全驱：共享文件交叉修改较多，容易产生隐蔽回归。

## 4. 架构与隔离边界

### 4.1 构型判定

新增或复用集中式判定接口，分别表达“当前是否为全驱机架”和“当前是否为飞行汽车机架”。所有特殊控制逻辑必须通过相应判定接口启用，不能仅凭一个通用参数影响其他机型。

- 全驱判定仅接受 6003、6004 及其已有仿真包装机架；
- 飞车判定仅接受 80003 及其对应的 80003 SITL 包装机架；
- 两个集合互斥；
- 不匹配时使用 PX4 原始实现和默认参数。

### 4.2 6003 全驱六旋翼

6003 继续使用现有 `FixedFullyActuatedHexa` 旋翼轴配置、六自由度姿态/位置控制和全驱专用伪逆分配器。其 `CA_AIRFRAME=16` 仅在全驱机架判定成立时生效。

### 4.3 6004 全驱六旋翼加机械臂

6004 继承 6003 的飞行参数与控制链，额外启用 HX-30HM 机械臂模块、RC AUX 映射和 Pixhawk 6C TELEM2 串口配置。机械臂执行器不进入飞行控制分配矩阵。

### 4.4 80003 飞行汽车

80003 使用标准四旋翼控制分配和四旋翼姿态/位置控制，不得进入 `FixedFullyActuatedHexa` 路径。它额外启动飞车模式管理与差速轮模块：

- 飞行状态由标准四旋翼控制链驱动四个旋翼；
- 地面状态由差速轮控制链驱动车轮；
- `RD_MOT_OFFSET=4` 将车轮输出放在四个飞行电机之后；
- 状态机负责飞行/地面模式互锁，防止不安全的执行器交叉控制。

### 4.5 普通 PX4 机型

例如 `4001_quad_x` 的普通四旋翼不加载飞车应用，不创建飞车模式状态，不启用全驱控制器，也不更改差速轮输出。所有共享文件修改必须存在明确的负向回归测试。

## 5. 启动和数据流

统一启动流程如下：

`SYS_AUTOSTART` → 对应机架脚本 → 构型专属默认参数与应用 → Commander 构型判定 → 对应控制器 → 对应执行器映射。

具体行为：

- 6003 加载多旋翼默认值和全驱六旋翼参数；
- 6004 先加载 6003，再加载机械臂和串口参数；
- 80003 加载飞车默认值、标准四旋翼几何和差速轮输出偏移，并启动飞车应用；
- 其他机型沿用原有机架脚本与应用列表。

## 6. 组件合并策略

### 6.1 Commander

以全驱版本的 `Commander.cpp`、`Commander.hpp` 和构建定义为基准，嵌入 `FlyingCarMode`。保留全驱地面滑行/状态订阅逻辑，同时确保飞车状态机只为 80003 创建和运行。源目录中的 Commander 备份文件不复制。

### 6.2 控制分配和多旋翼控制器

保留全驱版本的 control allocator、控制分配库、姿态控制和位置控制实现。80003 不替换这些实现；如飞车代码对起飞或普通多旋翼控制存在必要修正，则以最小条件分支引入，并为普通四旋翼增加回归用例。

### 6.3 差速轮模块

移植 80003 使用的轮输出偏移和映射支持，包括相关参数元数据及测试。原有 rover differential 行为保持不变；飞车专属映射只有在 80003 判定成立时生效。

### 6.4 ROMFS 和机架注册

合并 `init.d`、`init.d-posix` 及其 CMake 注册，保留 6003、6004 和现有全驱仿真包装，同时加入 80003 真机与 Gazebo Classic 包装。注册项必须唯一，引用的脚本必须存在。

### 6.5 Pixhawk 6C

以全驱版本 `boards/px4/fmu-v6c` 为基准，保留全驱和机械臂模块；补充 80003 所需的 Commander/rover 模块和启动支持。TELEM2 的机械臂占用只由 6004 的参数配置触发。

### 6.6 Gazebo Classic 与测试工具

只复制 80003 实际引用的 FS-FASMv8 四旋翼飞车模型、世界和 launch 链，以及 `Tools/flying_car_test` 中支持 80003 的实验与验证工具。模型名、`PX4_SIM_MODEL` 与 airframe wrapper 必须一一对应。

## 7. 错误处理与安全约束

- 80003 请求全驱专用 `CA_AIRFRAME=16` 时拒绝该组合并产生明确告警；
- 6003/6004 尝试启用飞车模式或差速轮专属映射时拒绝启用并产生明确告警；
- 机架判定失败或参数不匹配时回退到 PX4 原有控制路径；
- 飞车模式切换必须保留执行器互锁，模式状态无效时采用安全停止行为；
- 机械臂串口冲突处理仅由 6004 机架脚本执行，不影响 6003、80003 和普通机型。

## 8. 验证策略

### 8.1 静态检查

- 确认 6003、6004、80003 注册唯一；
- 确认所有 shell、CMake、模型和 launch 引用目标存在；
- 确认目标目录不包含源代码备份和已有 build 输出；
- 确认全驱机架集合与飞车机架集合互斥。

### 8.2 单元与专项测试

- 全驱机架判定正向和负向测试；
- 飞车机架判定正向和负向测试；
- `FlyingCarMode` 状态转换与安全互锁测试；
- 差速轮输出偏移和映射测试；
- 80003 机架/模型/launch 契约测试；
- 4001 普通四旋翼负向隔离测试；
- 保留并运行全驱控制分配、姿态控制和位置控制测试。

### 8.3 构建验证

- 构建 `px4_fmu-v6c_default`；
- 构建已有全驱 SITL 目标；
- 构建 80003 Gazebo Classic SITL 目标；
- 在可用环境中运行 80003 Gazebo Classic 启动冒烟测试。

如果 Windows 主机缺少 NuttX 或 Gazebo Classic 工具链，则先运行所有平台无关测试和静态检查，并记录需要在 WSL/Linux 环境执行的具体命令及未验证项，不将“工具链不可用”误报为代码通过。

## 9. 完成标准

- 新目录 `D:\PX4-v1.17` 独立存在，两个源目录内容未被修改；
- 6003、6004、80003 可从同一代码树通过 `SYS_AUTOSTART` 选择；
- Pixhawk 6C 固件构建配置同时包含全驱、机械臂和飞车所需模块；
- 6003/6004 的全驱行为和 6004 机械臂行为保持不变；
- 80003 的真机配置、Gazebo Classic 模型和测试链完整；
- 4001 普通四旋翼的负向隔离测试通过；
- 所有可运行的测试和构建均通过，无法在当前主机执行的项目有明确记录。
